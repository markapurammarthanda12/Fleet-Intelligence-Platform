# ADR 0002 Adopt Kafka for durable telemetry ingress

- Status: Accepted for the current implementation; HA and scale settings remain deployment requirements
- Context: The challenge expects durable replayable messaging. Direct synchronous API-to-database writes would couple ingress availability and throughput to PostgreSQL and would not provide a retained stream for replay.
- Decision: Validate requests at the Spring Boot API, publish keyed events to a 12-partition Kafka topic with idempotent producer settings and `acks=all`, and let a consumer group apply event-time rules and persist events in PostgreSQL. Retain the local topic for seven days, retry processing with bounded retry topics, and route exhausted failures to a dead-letter topic. Keep the database uniqueness constraint on `(tenant_id, event_id)` as the idempotency boundary. Use a single broker only in the local Compose environment; shared deployments must use at least three brokers with replication factor 3 and minimum in-sync replicas 2. Add a separate time-series or columnar store only after measuring query and ingest workloads.
- Consequences: Ingress acknowledges after broker confirmation rather than after database writes, so reads may briefly lag. Kafka decouples ingress from consumer pace and retains events for replay. Database uniqueness protects against at-least-once delivery. The local broker still has a single point of failure, uses plaintext transport, and has not been benchmarked at challenge scale; production TLS, multi-broker deployment, replay runbooks, and performance evidence remain outstanding.
