# ADR 0002 Adopt Kafka for durable telemetry ingress

- Status: Accepted for the current implementation; HA and scale settings remain deployment requirements
- Context: The challenge expects durable replayable messaging. Direct synchronous API-to-database writes would couple ingress availability and throughput to PostgreSQL and would not provide a retained stream for replay.
- Decision: Validate requests at the Spring Boot API, publish keyed events to a 12-partition Kafka topic with idempotent producer settings and `acks=all`, and use independent consumer paths: the application consumer applies event-time rules and persists operational state in PostgreSQL; ClickHouse's Kafka Engine and materialized view copy events into a MergeTree analytical table. Retain the local Kafka topic for seven days and ClickHouse history for 90 days, retry application processing with bounded retry topics, and route exhausted failures to a dead-letter topic. PostgreSQL uniqueness on `(tenant_id, event_id)` protects the operational path. Use a single broker only in local Compose; shared deployments need at least three brokers with replication factor 3 and minimum in-sync replicas 2.
- Consequences: Ingress acknowledges after broker confirmation rather than after either store writes, so both query paths may briefly lag. Separate consumer groups let operational processing and analytical history proceed independently. The hourly Reports API deduplicates Kafka redelivery when counting unique event IDs. The local broker is still a single point of failure, uses plaintext transport, and the ClickHouse path has not yet been verified end to end. Production TLS, multi-broker deployment, replay runbooks, and performance evidence remain outstanding.
